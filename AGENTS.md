# AGENTS.md — gcs-versioning-bot

## Purpose

`gcs-versioning-bot` is the central semantic versioning engine for Partior's CI/CD pipelines. Given two importer files produced by `gcs-yaml-importer`, it queries the current artifact version from JFrog Artifactory (or Jira), evaluates versioning rules against branch context and commit messages, and computes the next incremented version string. It outputs the version for downstream packaging, tagging, and promotion steps.

## Tech Stack

- **GitHub Actions** — Composite action (`runs: composite`)
- **Shell (bash)** — All versioning logic in `scripts/`
- **JFrog Artifactory REST API** — Queries current artifact version
- **Jira REST API** — Optionally queries Jira version (when `version-sources.jira.enabled: true`)
- **Semantic Versioning 2.0** — Version format: `MAJOR.MINOR.PATCH[-prerelease][+build]`
- **yq** — YAML parsing within scripts

## Architecture Patterns

- **Importer-driven configuration**: All versioning rules come from two importer files (shell scripts sourced at runtime) generated by `gcs-yaml-importer`. The action itself contains no hardcoded project configuration.
- **Source files (`.tmp`)**: Intermediate state is written to scratch `.tmp` files (`source-*.tmp`) during the run and read by subsequent script steps.
- **Rule evaluation chain**: The bot evaluates rules in priority order: branch name → commit message tags → PR labels → file-based version → Jira version.
- **Pre-release identifiers**: Branch-to-identifier mapping is configurable; defaults are `dev` for feature/develop and `rc` for release branches.
- **Version file replacement** (optional): Can update `pom.xml`, `helm/Chart.yaml`, or a custom token file with the computed version in-place.

## Coding Conventions

- Scripts in `scripts/` use `set -euo pipefail` and are named with lowercase hyphens.
- Importer file inputs are sourced (`. "$FILE"`) to inject flat variables into the shell environment.
- Scratch files (`*.txt`, `*.tmp`) are written to the action workspace, not to system temp dirs.
- Version bump tag filenames (`MAJOR_GH_CURRENT_MSGTAG`, etc.) are read by the scripts at runtime — do not rename or move them.
- YAML config keys use kebab-case (e.g., `artifact-base-name`). After importing, they become underscore variables (e.g., `artifact-base-name` → `artifact-base-name`). Handle both forms in scripts.
- All API credentials come from inputs — never hardcode.

## Testing

- Integration tests run via GitHub Actions using `test-files/` and `test-files-demo/` fixtures.
- The test workflow (see README for the sample workflow) triggers a full versioning run and validates `artifact-version-name` output.
- To test locally: export all `INPUT_*` variables and source the importer files manually.
- Test matrix should cover: `main` branch (release), `develop` branch (dev), `release/*` branch (RC), message-tag bumps, and Jira-enabled mode.

## Key Abstractions

| Abstraction | Description |
|-------------|-------------|
| `versioning-rules-importer-file` | Sourced script providing `artifact-base-name`, `artifact-auto-versioning.*` rules |
| `branch-packager-rules-importer-file` | Sourced script providing branch-specific rules (packager config, group, etc.) |
| Version source query | `scripts/` queries Artifactory or Jira for the current DEV/RC/RELEASE version |
| Rule evaluator | Determines which version component to bump and which pre-release identifier to append |
| Scratch files | `artifact_last_*.txt`, `artifact_next_version.txt` — intermediate state between script steps |
| Message tags | Commit messages containing `MAJOR_GH_CURRENT_MSGTAG` etc. force specific bumps |

## Agentic Task Guidance

✅ **Safe to update** `controller-config-files/projects/default.yml` to add new optional config keys.  
✅ **Safe to add** new version source types (e.g., a GitHub tag source) by adding a new script and gating it with an `enabled` flag.  
✅ **Safe to update** Artifactory or Jira API calls if endpoint formats change.  
⚠️ **Be careful** modifying the rule evaluation order in `scripts/` — rules have documented priority; changing priority is a breaking change.  
⚠️ **Be careful** changing scratch file names (`artifact_*.txt`) — multiple scripts read and write these files by name.  
⚠️ **Be careful** with the importer file sourcing — the flat variable names depend on the YAML key paths; changing config key names is a breaking change for all callers.  
❌ **Do not** hardcode version numbers or artifact names in any script.  
❌ **Do not** push to `partior-stable` without running the full test workflow and validating outputs against `test-files/`.  
❌ **Do not** log Artifactory passwords or Jira API tokens.

## External Dependencies

- **Jira REST API** — `https://partior.atlassian.net` — optional, for Jira-sourced versioning

- **`curl`** — HTTP client for API queries (standard on all runners)

## Common Pitfalls

- **Missing importer files**: Both `versioning-rules-importer-file` and `branch-packager-rules-importer-file` are required. If either is missing or contains no variables, the bot will compute incorrect versions or fail silently.
- **Wrong `query-path` in gcs-yaml-importer**: The versioning rules importer must be scoped to `.smc.ci` (not `.smc.ci.artifact-auto-versioning`), and the branch importer must be scoped to `.smc.ci.branches.<branch-name>`. Wrong paths produce empty importers.
- **Branch name detection**: The bot auto-detects the branch from `GITHUB_REF_NAME` or `GITHUB_HEAD_REF`. Override with `branch-name` input only for testing — wrong branch name produces wrong pre-release identifiers.
- **Scratch file pollution**: If a workflow retries a failed step, scratch files from the previous attempt may still exist on the runner. The scripts should overwrite, not append.
- **Jira version format**: Jira version identifiers must match the project's release naming convention exactly; a mismatch causes the Jira version source to return no result and fall back to Artifactory.
- **`artifact-type: docker`**: Docker images use a different Artifactory API endpoint for version querying. Always set `artifact-type: docker` for Docker image versioning.
